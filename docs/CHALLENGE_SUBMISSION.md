# Challenge Submission Process

> How to submit a soundness challenge to actenon-scan, and what
> happens after you do.

This document is the process counterpart to
[`community-scans/CHALLENGE_TEMPLATE.md`](../community-scans/CHALLENGE_TEMPLATE.md)
(the submission template) and
[`docs/SOUNDNESS_CHALLENGE.md`](SOUNDNESS_CHALLENGE.md) (the live
scoreboard). Together, the three documents are the public embodiment
of the rule stated in [`docs/COVERAGE.md`](COVERAGE.md): **silence
must never imply safety**.

If you are reading this because scan reported a finding you believe
is wrong, or because scan reported clean on code you believe is
dangerous, you are in the right place.

---

## Where to submit

Two equally valid routes:

### 1. GitHub issue (fastest)

Open an issue on
[`https://github.com/Actenon/actenon-scan/issues`](https://github.com/Actenon/actenon-scan/issues)
and apply the **`soundness-challenge`** label. Paste the metadata
fields from
[`community-scans/CHALLENGE_TEMPLATE.md`](../community-scans/CHALLENGE_TEMPLATE.md)
into the issue body. Attach the fixture file inline as a code block,
or paste a link to a gist.

If a fixture file is too large to fit inline (more than ~100 lines,
which usually means it is not minimal), use route 2.

### 2. Pull request (preferred for fixtures)

Open a PR that adds two files:

- `tests/challenge/CHALLENGE-NNN.yml` — the metadata, using the YAML
  form in the template. Pick `NNN` as the next available number after
  the highest existing challenge file in that directory.
- `tests/challenge/CHALLENGE-NNN.<ext>` — the minimal reproducing
  fixture, mirroring the pattern of
  [`CHALLENGE-001.go`](../tests/challenge/CHALLENGE-001.go): a comment
  header naming the challenge, the source, and what it demonstrates,
  then the smallest code that reproduces the defect.

The PR will not be merged until the case is triaged. If the case is
rejected, the PR is closed with a reason; if accepted, the PR is
merged and the scoreboard is regenerated.

### What we need in every submission

Regardless of route:

- **A fixture file** — a single source file in Python, TypeScript, or
  Go that reproduces the defect when scanned.
- **The exact scan command** you ran (including any `--guard`,
  `--config`, or `--repository-analysis` flags).
- **The scanner version** (`actenon-scan --version`).
- **The observed output** — paste the relevant lines from the scan
  report (the finding line, or the "0 findings in N files" summary).
- **The expected output** — what scan should have said, and a 1–3
  sentence explanation of why.

## What happens after submission

### Acknowledgement (≤ 30 days)

Every submission receives a public first response within 30 days.
That response may be nothing more than "received, triage queued" —
the point is that the channel is not silent. If 30 days pass with no
maintainer response, ping the issue; that itself is a process bug we
want to hear about.

### Triage

After acknowledgement, the maintainer inspects the fixture against
the current scanner output. The questions are:

1. **Is the defect real?** Does scan's output on this fixture actually
   differ from what an honest analyst would say?
2. **Is it in scope?** Is the language supported? Is the defect already
   documented in [`docs/COVERAGE.md`](COVERAGE.md) as NOT COVERED? Is
   it a configuration issue (`--guard`, custom sink) rather than a
   detector defect?
3. **Is it a duplicate?** Is it the same defect as an existing open or
   fixed case in
   [`docs/SOUNDNESS_CHALLENGE.md`](SOUNDNESS_CHALLENGE.md)?

The triage outcome is one of:

- **`accepted`** — the case is a soundness defect. It is added to the
  scoreboard immediately, *before* it is fixed. The open miss is
  visible from the moment of acceptance.
- **`rejected`** — the case is not a soundness defect. The maintainer
  states why (out of scope, documented limitation, configuration, or
  the analysis is actually correct on this fixture).
- **`wontfix`** — the case is a real defect but the maintainer
  declines to fix it, with the reason recorded publicly. The case
  remains visible on the scoreboard as a known limitation.

### Scoreboard entry

Accepted cases are added to
[`docs/SOUNDNESS_CHALLENGE.md`](SOUNDNESS_CHALLENGE.md), which is
regenerated by
[`scripts/generate_soundness_scoreboard.py`](../scripts/generate_soundness_scoreboard.py)
from the `tests/challenge/CHALLENGE-NNN.yml` files. The submitter's
GitHub handle is recorded in both the scoreboard row and the fixture
file header.

### Fixture port

For PR submissions the fixture is already in place. For issue-only
submissions, the maintainer ports the fixture into
`tests/challenge/CHALLENGE-NNN.yml` and `CHALLENGE-NNN.<ext>` as part
of acceptance, credited to the submitter.

## The lifecycle

```
                  submitted
                      │
                      ▼
            acknowledged (≤ 30 days)
                      │
                      ▼
                   triaged
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
    accepted      rejected       wontfix
        │             │             │
        ▼             │             │
  added to scoreboard │             │
  (open miss visible) │             │
        │             │             │
        ▼             │             │
  fixture ported to   │             │
  tests/challenge/    │             │
  (expected-to-fail) │             │
        │             │             │
        ▼             │             │
       fixed          │             │
        │             │             │
        ▼             │             │
  fixture flipped to  │             │
  expected-to-pass    │             │
  (regression test)   │             │
```

The lifecycle is deliberately asymmetric: an **accepted** case is
visible on the scoreboard from the moment of acceptance, regardless
of how long it takes to fix — or whether it is ever fixed. The
scoreboard's open cases section is the load-bearing part of this
channel. A scoreboard that only showed fixed cases would be a trophy
cabinet, not a safety mechanism.

## Disclosure policy

### Submissions are public by default

The fixture, the metadata, the triage discussion, and the scoreboard
entry all live in this repository in plain text. This is the opposite
of a private vulnerability disclosure programme. The point of the
channel is to make scan's blind spots visible to anyone who reads the
scoreboard.

This is consistent with
[`DISCLOSURE_POLICY.md`](../DISCLOSURE_POLICY.md), which applies the
same publication-by-default posture to challenge cases as to
maintainer-requested scans.

### Reporter credit

The reporter's GitHub handle is recorded in two places when a case is
accepted:

1. The scoreboard row in
   [`docs/SOUNDNESS_CHALLENGE.md`](SOUNDNESS_CHALLENGE.md).
2. The fixture file header comment, e.g.:

   ```go
   // Challenge case: <title>.
   // External submission credited to @<handle>.
   // See CHALLENGE-NNN.yml for metadata.
   ```

Credit persists when the case is fixed. We do not retroactively strip
credit from resolved cases.

### Anonymisation

If you do not want your handle attached, submit with
`submitted_by: anonymous`. The case is recorded as anonymous in both
the scoreboard and the fixture header. We will not publish a name you
did not provide.

If your fixture is derived from a real codebase and you do not want
that codebase named, strip the fixture down to a minimal reproducing
case that does not identify the source — the pattern in
[`tests/challenge/CHALLENGE-001.go`](../tests/challenge/CHALLENGE-001.go)
is the model: derived from `anthropic-sdk-go` but the fixture body
does not name it.

### Boundary with vulnerability disclosure

This channel is for defects in **scan's analysis** — places where scan
says the wrong thing about code that exists. It is **not** for
vulnerabilities in third-party codebases that scan happens to have
flagged correctly. If scan reported a real, consequential,
agent-reachable defect in someone else's code, that is scan working
as designed; report it to that codebase under their security policy,
not here.

The boundary is stated in [`SECURITY.md`](../SECURITY.md):
"vulnerabilities in actenon-scan itself" belong to the private
disclosure route (security@actenon.dev); vulnerabilities in scanned
code belong to the scanned codebase's policy; **soundness defects in
scan's analysis** belong here, in public.

## Acceptance criteria

A submission is **`accepted`** when the maintainer confirms it is a
soundness defect — that is, scan's output on the fixture differs from
what an honest analyst would say, in a way that could mislead a
reviewer reading the report.

Acceptance is **independent of fix status**. A case can be accepted
and remain open on the scoreboard for months while the underlying
detector is reworked. The scoreboard's "Open cases" section is the
list of accepted-but-unfixed defects; it is the load-bearing safety
signal of this channel.

Concretely, a case is accepted when one of these holds:

- **`false-positive`** — scan reports a finding where the truth is
  no-finding. Examples: a guard in the recognised vocabulary dominates
  the sink and scan missed it; no model-controlled input reaches the
  sink on the analysed path; the sink is not actually a consequential
  action under the rule's definition.
- **`missed-sink`** — scan reports clean where the truth is a finding.
  Examples: a supported-language sink reachable from a recognised
  agent boundary that scan does not flag; a guard scan accepts that is
  actually defeated (in a branch the sink does not share, placed after
  the sink, in a nested scope).
- **`wrong-classification`** — scan flags the right call but mis-states
  a property (severity, category, guard dominance, binding state,
  reachability reason) in a way that would mislead a reviewer.

A case is **`rejected`** when the maintainer determines scan's output
on the fixture is actually correct, or the defect is out of scope
(unsupported language, documented limitation, configuration issue,
duplicate of an existing case). A rejected case is closed with the
reason, and is not added to the scoreboard.

A case is **`wontfix`** when the maintainer confirms the defect is
real but declines to fix it, with the reason recorded. The case
remains on the scoreboard as a known limitation. This is the honest
outcome when a fix would require rearchitecting a detector in a way
that creates more risk than the defect itself.

## What we commit to

1. **A public response to every submission within 30 days.** No
   silent ignoring. If we miss this, ping the issue — that is itself
   a process bug.
2. **Public triage outcomes.** Accepted, rejected, and wontfix are
   all recorded on the issue or PR. No private acceptances.
3. **Reporter credit, by handle or anonymous, in the scoreboard and
   the fixture.** Credit persists when the case is fixed.
4. **Accepted cases become permanent regression tests when fixed.** A
   fixed case flips from expected-to-fail to expected-to-pass and
   stays in `tests/challenge/` forever. Regressions on a fixed case
   fail the build.
5. **Open misses stay visible.** The scoreboard's open cases section
   is the load-bearing part of this channel. We do not remove
   accepted-but-unfixed cases to make the scoreboard look cleaner.

What we do **not** commit to:

- A fix timeline. Some accepted cases will be fixed in the next
  release; some will stay open for months; some may never be fixed
  and remain visible as known limitations. What we promise is
  visibility, not closure.
- A CVE or formal advisory. Challenge cases are defects in scan's
  analysis, not vulnerabilities in scanned code. They are published
  as fixtures and scoreboard entries, not as security advisories.
- A bounty. There is no financial reward. The reward is a permanent
  regression test credited to your handle and a scoreboard entry
  that documents the boundary of what scan can see.
